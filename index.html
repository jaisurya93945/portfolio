    01Selected work
    AI Threat Gateway v0.4.0 · MIT

    SentinelCore

    A security layer between an AI application and the models, tools and data it touches — inspecting prompts, retrieved context, tool calls, MCP tool definitions and model output, then enforcing a policy on what happens next.

    Source

    The problem

    An AI application exposes a model to untrusted user input, external documents, tools and other AI systems. That is a security boundary traditional AppSec never covered: the request is well-formed, the token is valid, the tool is permitted — and the content still decides what happens.

    What it does

    Five detectors run over every origin — input, each retrieved document, and output. Their findings feed a deterministic risk score and a configurable policy engine, which returns one of five decisions. As a reverse proxy it is OpenAI-path compatible, so it scans the response as well as the request, streaming included.

    Evidence

    • 96.8%precision
    • 17.7%recall
    • 0.5%false-positive rate
    • 744labelled examples

    345 malicious, 399 benign, from two MIT-licensed public sources. The recall is the honest signature of a rule-and-heuristic detector: it rarely cries wolf, and it misses most real-world attacks. The repository says so in those words, and an attack-replay lab tracks every version against the same set — v0.1 to v0.3, twenty attacks newly caught, zero regressions.

    03Research

    NeuroGenesis · open research

    Does provable identifiability predict empirical symbol grounding?

    A neuro-symbolic model can score the right label through the wrong concepts and still satisfy its knowledge base. Accuracy looks fine; interpretability and out-of-distribution behaviour are gone. Theory can decide before training whether a constraint set pins the concept mapping down. This asks whether that prediction survives contact with gradient descent.

    • 1010candidate maps pruned in ~1 ms
    • 2,000differential comparisons, exact agreement
    • 47oracle correctness tests passing
    Source
    SentinelCoreablation study · 170 agent traces

    Does knowing where a prompt came from make a gateway safer?

    Given a ground-truth detector, provenance-aware policy adds 47 points of attack prevention at no cost to legitimate work. Given a real learned detector it adds 2.4 points, not statistically significant, and costs about 9 points of benign completion. Oracle evaluation overstates the mechanism by roughly 20× — and the misleading result is the one that is statistically solid.

    • H1Detection recall, not policy, is the binding constraintstands · APR 0.28 → 0.94
    • H2Provenance-aware risk scoring raises attack preventionfalsified · 0 of 37 decisions changed
    • H3Applying provenance to the policy rule instead of the score fixes H2falsified · 0 of 37
    • H4Provenance is free — measured under an oracle detectorsuperseded, kept unedited
    • H5Oracle evaluation systematically overstates anything layered on detectionstands · ≈20×
    • 0.185 → 0.884recall, rules vs learned · 10 seeds
    • 4.78×representative improvement
    • p ≤ 5.6×10⁻⁶McNemar, 10 of 10 seeds
    • 149 / 170payloads written by someone else

    H2 and H3 failed for one reason: provenance re-weights findings that already exist. The four attacks surviving every configuration produced zero findings, and zero multiplied by any trust factor is still zero. The first run used 37 self-authored traces with ±18-point intervals, so the honest next step was five times more traces rather than another mechanism — the current benchmark takes its attack text from a held-out public split instead of writing it here.

    07About

    I work on the seam between a model and everything it is allowed to touch. That seam is where the interesting failures live: a tool call whose argument came from a web page, a retrieved document that carries an instruction, a prompt that reaches a model with more authority than the person who sent it.

    Most of what I build is deliberately boring in its decision path. SentinelCore's verdicts come from rules you can read; IdenSec keeps the model out of the decision entirely. That is a choice, not a limitation — a security control you cannot explain is one you cannot defend in a review.

    I came to this from security operations rather than from research: SIEM alerts, vulnerability assessment, incident response, then DevSecOps and cloud. That order matters. I am less interested in whether an attack is novel than in whether the thing I shipped will hold on a Tuesday afternoon when nobody is watching it.

    What I want next is work where the security of AI systems is the product, not an afterthought bolted on before launch — building defences, red-teaming them honestly, and publishing what did not hold.
